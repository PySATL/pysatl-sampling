# Подготовка и публикация коммита

Работай в корне Git checkout. Прочитай [правила проекта](../../../CONTRIBUTING.md) и [workflow проверок](../../../.github/workflows/git_conventions.yml). Запрос на подбор названия заканчивается вариантами названия. Запрос на публикацию через этот skill охватывает коммит и push выбранных изменений.

1. **Согласуй состав.** Посмотри `git status --short --branch --untracked-files=all`, обычный и staged diff, текущую ветку, remotes и коммиты ветки сверх базы. Покажи пользователю компактный список, укажи уже staged файлы и спроси, какие пути включить. Если пользователь уже перечислил пути, используй этот выбор. Для файла с частичным staging уточни, нужны ли staged hunks или весь файл. Учитывай обе стороны переименования.
2. **Выбери ветку и автора.** Используй подходящую рабочую ветку пользователя или создай новую от актуальной main по правилам проекта. Сохрани незавершённые изменения и индекс. Для участника команды используй его ветку в проекте, для внешнего автора — ветку в его fork. Проверь фактический push URL. Сверь имя и email через `git var GIT_AUTHOR_IDENT` и `git var GIT_COMMITTER_IDENT`. Используй настроенную личность автора и его доступ к remote. Если личность или назначение неоднозначны, уточни их перед записью. Не подставляй чужие данные из истории.
3. **Проверь выбранные изменения.** Для Markdown, обычного текста и PDF пропусти стилевые проверки. Для изменённых C/C++ исходников и заголовков примени `clang-format -i --style=file <файлы>` по стилю проекта, проверь результат через `clang-format --dry-run --Werror --style=file <файлы>`. Запусти `clang-tidy -p <build-dir> <translation-units>` с реальной compilation database; изменения заголовков проверь через включающие их translation units. Для удаления файла проверь затронутую сборку. Выполни подходящие build, tests и проверки других языков по README и CI. Для частичного staging проверяй и форматируй выбранный снимок в изоляции, сохраняя остальные hunks. Если для C++ ещё нет стиля, точных флагов или toolchain, выясни применимую конфигурацию и явно сообщи, что осталось непроверенным, прежде чем предлагать публикацию с пропуском.
4. **Предложи название.** По фактическому diff дай 2–3 подходящих заголовка и предложи выбрать один. Формат — `type(scope): description` или `type: description`. Типы коммитов — `feat`, `fix`, `refactor`, `test`, `struct`, `ci`, `docs`, `chore`. Тип `repo` допустим только для ветки. Начинай описание с английского глагола в imperative со строчной буквы, без точки в конце. Например, `docs: explain sampler ownership`. Если пользователь уже дал корректный заголовок, используй его. Покажи целевую ветку, remote и дополнительные исходящие коммиты, если они есть; включение посторонней истории требует явного согласия.
5. **Зафиксируй выбранный снимок.** Добавляй пути явно через `--`. Перед коммитом сверь весь предлагаемый diff с согласованным выбором. Если в индексе есть чужие staged изменения, используй изолированный индекс от HEAD либо path-limited commit для целиком выбранных файлов. Учти, что `git commit --only -- <paths>` берёт рабочие версии этих файлов. После коммита сверь список путей, содержимое, автора и сохранность остальных staged изменений.
6. **Проверь историю и отправь.** Запусти из корня на полной истории с Python 3.12, как в CI (замени `origin/main` на фактическую базу проекта при работе через fork):

   ```sh
   PYSATL_COMMIT_BASE=origin/main PYSATL_COMMIT_HEAD=HEAD python3 .github/scripts/check_git_conventions.py
   ```

   Проверка без `PYSATL_COMMIT_HEAD` пропускает заголовки коммитов. После успешной проверки выполни обычный `git push -u <remote> HEAD:refs/heads/<ветка>` для согласованной публикации. При отказе non-fast-forward проверь расхождение истории до синхронизации; проект использует rebase, принудительный push требует отдельного решения автора. Сообщи SHA, ветку, remote, результаты проверок и push. Дальнейший путь проекта — PR и ревью maintainer. Автор самостоятельно PR не сливает.
