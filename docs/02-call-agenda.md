## 0. Что я уже выяснил (2 минуты в начале)

1. UNU.RAN — ~127 тыс. строк C, архитектура «ООП на C»: `distr → par → gen`, vtable руками, `void*`-downcast макросами, ~40 методов и ~40 распределений. **Objective-C там нет**: GitHub так размечает `.h`, где в комментариях Texinfo-строки `@end itemize`.
2. Наш форк `PySATL/unuran` в pysatl-core не используется: submodule закреплён на последнем коммите scipy, собирается UNU.RAN **1.9.0** (upstream — 1.12.0).
3. pysatl-core использует 6 методов из ~40, только univariate, без seed, без параметров методов.
4. Нашёл воспроизводимый **segfault** (double free `par` при неуспешном `unur_init`) на пути, который должен уходить в fallback.
5. Обвязка в ~38 раз медленнее, чем тот же UNU.RAN в SciPy (837 против 22 ns на variate), всё уходит на Python-callback на каждый U(0,1) и Python-цикл.

## 1. ★ Цели глобального рефакторинга

Главный вопрос созвона: **что считается успехом проекта?** От ответа зависят и архитектура, и объём ВКР. Возможные цели (могут комбинироваться, но приоритет нужен):

| # | Цель | Что значит на практике | Метрика успеха |
|---|---|---|---|
| G1 | **Сопровождаемость** | команда может читать, чинить и расширять код без экспертизы в C-ООП | CI, тесты, доки; время на добавление метода |
| G2 | **Корректность и безопасность** | нет UB/утечек/double free, ошибки как исключения, thread-safety | ASan/UBSan/TSan чистые; fuzzing; тесты против оригинала |
| G3 | **Производительность в Python** | сэмплинг сравним с SciPy/NumPy | ns/variate, setup time; бенчмарки vs scipy.stats.sampling |
| G4 | **Независимость и лицензия** | свой проект под своим именем и (возможно) своей лицензией | юридически чистый статус, переименование |
| G5 | **Расширяемость под PySATL** | методы, которых нет в UNU.RAN; интеграция с графом характеристик pysatl-core; multivariate | новые методы/распределения, покрытие API |
| G6 | **Научная новизна для ВКР** | не только «переписали», а что-то измеримое: новый дизайн API, compile-time выбор метода, SIMD/batch sampling, верификация | то, что можно защищать |

## 2. ★ Стратегия: варианты и trade-offs

| Вариант | Суть | + | − | Когда выбирать |
|---|---|---|---|---|
| **A. Обёртка** | C-ядро как есть (обновить до 1.12), сверху C++23 RAII-обёртка + nanobind/pybind11 | быстро (недели), 100% поведения оригинала, сразу чинит perf и segfault | техдолг C остаётся, лицензия/имя не меняются по сути, мало новизны для ВКР | цель — G3 быстро |
| **B. Поэтапная миграция (strangler fig)** | C++ API + Python-биндинги на старом ядре, затем методы переписываются по одному (PINV → TDR → DGT → …), каждый проверяется против C-версии | всегда работающая система, есть oracle для тестов, риск размазан | долго живут два кода; нужен слой совместимости `distr`/`gen` | цель — G1+G2+G3, срок ВКР ограничен |
| **C. Полный rewrite с нуля** | новый дизайн на C++23, UNU.RAN — только справочник алгоритмов (статьи Hörmann/Leydold) | максимальная свобода дизайна, чище лицензионно (особенно clean-room), больше новизны | очень большой объём (~40 методов), высокий риск не довести, регрессии в численных краях, которые UNU.RAN уже отладил за 20 лет | цель — G4+G6, и можно урезать скоуп до ~5–8 методов |
| **D. Гибрид B+C** | новое ядро с нуля, но только для методов, нужных pysatl-core (PINV, TDR, AROU, HINV, NINV, DGT + DAU), остальное — через обёртку C | реальный объём ВКР, сравнение «новое vs оригинал» встроено | всё ещё две кодовые базы | моя рекомендация по умолчанию |

Вопросы:
- ★ Какой вариант приемлем по срокам (сколько семестров на НИР + ВКР)? Минимальный набор методов, который должен быть в итоге?
- Нужно ли сохранять String API (`"normal(0,1) & method=pinv"`) и парсер функций? Это ~10 тыс. строк, pysatl-core их не использует.
- Multivariate (`cvec`, MVTDR, HITRO, GIBBS) в скоупе или нет?

## 3. Архитектура C++23 (что хочу обсудить, не решать)

- Типизация вместо runtime-кук: `Generator<Continuous>` / `Generator<Discrete>` — `unur_sample_cont` на discrete-генераторе становится ошибкой компиляции, а не UB (`KNOWN-PROBLEMS`).
- Распределение как concept (`requires { d.pdf(x); }`) вместо структуры с 20 nullable указателями; разделение setup (дорогой, строит таблицы) и sample (дешёвый, `const`, thread-safe).
- URNG: `std::uniform_random_bit_generator` + адаптер к NumPy `bitgen_t`; без глобального default; seed обязателен или явно случайный.
- Ошибки: `std::expected<Generator, SetupError>` для setup, исключения на границе Python; никакого `exit()` и глобального `errno`.
- Batch API `sample(std::span<double>)` — убирает Python-цикл; потенциально SIMD для PINV/DGT.
- Вопрос: `-fno-exceptions`-совместимость нужна? Целевые компиляторы и минимальные версии? Поддержка C++23 library features (`std::expected`, `std::mdspan`, `std::print`) в GCC/Clang/MSVC и особенно в Apple Clang/libc++ неравномерная, нужно свериться с cppreference compiler support перед фиксацией требований.

## 4. Python API и связь с pysatl-core

- ★ Биндинги: оставить CFFI или перейти на nanobind/pybind11? CFFI в API mode не умеет C++ напрямую, нужен `extern "C"`-слой. nanobind даёт RAII-ownership, массивы без копий, меньше бинарь; pybind11 — привычнее.
- ★ Где живёт код: отдельный пакет (`pysatl-unuran`/новое имя) с wheels или по-прежнему vendored в pysatl-core через submodule?
- Callbacks из Python (pdf/cdf из графа характеристик) неизбежно медленные на setup — это ок? Или целимся в то, чтобы pysatl-core для стандартных распределений передавал аналитику в C++ (без Python-callback)?
- Seed/воспроизводимость: как pysatl-core хочет принимать RNG (`np.random.Generator`? seed?).
